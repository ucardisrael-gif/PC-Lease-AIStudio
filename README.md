# PC-LEASE — B2B Hardware & Laptop Leasing Platform

Исторический журнал прототипа сохранён в [docs/HISTORICAL_MAIN_CHANGELOG.md](docs/HISTORICAL_MAIN_CHANGELOG.md). [ROLLBACK.md](ROLLBACK.md) относится к прежнему прототипу; перед восстановлением данных используйте актуальную процедуру резервирования ниже и проверяйте её на отдельной базе.

Платформа долгосрочной и гибкой аренды (лизинга) и продажи восстановленных бизнес-ноутбуков и микро-ПК для юридических лиц и специалистов (Израиль / Global).

## Резервная копия локальной PostgreSQL

Для копирования локального кластера его необходимо **штатно остановить** и не запускать до окончания проверки копии. Остановите сервер приложения и PostgreSQL через `pg_ctl stop -D <путь к data/postgres> -m fast -w` из поставляемых с embedded-postgres инструментов. На Windows обычное принудительное завершение процесса может оставить `postmaster.pid`; не удаляйте этот файл вручную, пока не выяснено состояние базы. Если файл присутствует, копирование откажет.

При остановленной базе выполните `npm run db:backup:offline`. Команда создаёт новую папку в игнорируемом Git каталоге `data/backups`, не перезаписывает существующие копии и сверяет файлы по SHA-256. Ошибочная незавершённая копия непригодна. Копия содержит все данные клиентов и должна храниться с ограниченным доступом; файл `data/postgres-password` храните отдельно в защищённом месте. Перед заменой рабочей базы проверяйте восстановление на отдельном экземпляре. Процедура не защищает от одновременного запуска PostgreSQL другим процессом и не является автоматическим резервированием production.

На Windows стандартный серверный набор `node server/test-local.mjs` также проверяет копирование и восстановление отдельной временной базы с миграциями. Этот тест не проверяет сохранность конкретной рабочей резервной копии.

## Браузерная проверка админки

После установки зависимостей приложения и сервера запустите `npm run test:admin-browser`. Проверке нужен Playwright: установите его в окружение проекта или задайте `PC_LEASE_PLAYWRIGHT_PATH` как абсолютный путь к установленному пакету. Для нестандартного расположения Chrome можно задать `PC_LEASE_CHROME_PATH`; иначе на Windows используется стандартный Chrome, а при его отсутствии — браузер Playwright. Проверка создаёт отдельный временный PostgreSQL, использует вымышленные данные, запускает отдельные локальные серверы и не отправляет реальную почту. Рабочая база не используется. Проверка требует свободных локальных портов и запуска из корня проекта.

## Локальная серверная основа

Нужен Node.js 24 или новее. Установите зависимости сервера командой npm install --prefix server. Для локальной разработки используется отдельный PostgreSQL; он не затрагивает старый проект.

1. В первом терминале выполните npm run db:local и оставьте его открытым. При первом запуске создаются база в data/postgres и случайный пароль в data/postgres-password. Порт базы — 55432, доступ только с этого компьютера.
2. При первом запуске в другом терминале выполните npm run db:seed, чтобы добавить семь демонстрационных моделей. Команда не перезаписывает существующие товары. Затем во втором терминале выполните npm run server:dev. Сервер будет доступен на 127.0.0.1:3001. Для проверки используйте npm run server:test: он создаёт отдельную временную базу и удаляет только её после завершения.
3. Остановите процессы в терминалах после работы. Каталог data не входит в Git. Не передавайте и не публикуйте файл пароля или данные базы.

Каталог, тарифы, пользователи и заказы хранятся в PostgreSQL. Доступ к административным операциям проверяется на сервере; в панели есть группы для каталога и содержимого, заявок, пользователей и прав, склада, сервисных заявок, договорных черновиков и финансовых записей. Подробности реализации и проверок — в PROJECT_STATUS.md; действующие решения владельца — в разделе 0 SPECIFICATION.md.

Локальные заказы сохраняют снимок расчёта, а предложение можно скачать в PDF или отправить по почте. Учёт договорных черновиков и финансовых записей не означает юридическое подписание или проведение платежа. Для реального размещения необходимы отдельные настройка и проверка сервера, HTTPS, защиты и резервирования; подготовка конфигурации не означает, что сайт опубликован.

## Проектная почта

Локальный сервер читает настройки SMTP из .env.mail при наличии файла. Образец — .env.mail.example; пароль приложения хранится только в локальном файле. Команда npm run mail:verify проверяет соединение без отправки письма. Сервер поддерживает уведомления о заказах и обращениях и отправку клиенту запрошенного предложения PDF. Сохранение обращения или заказа и результат почтовой отправки учитываются отдельно; подтверждение SMTP не означает подтверждения прочтения. Для тестов используется имитатор почты.

## 📦 Быстрый старт на локальном компьютере

1. **Установка зависимостей:**
   ```bash
   npm install
   ```

2. **Запуск сервера разработки:**
   ```bash
   npm run dev
   ```
   Приложение откроется по адресу `http://localhost:3000` (или `http://localhost:5173`).

3. **Сборка для продакшена:**
   ```bash
   npm run build
   ```
   Готовые файлы будут в папке `dist/`.

## Структура проекта

- src/components — публичные страницы; src/components/backoffice — тематические разделы админки.
- src/data и src/domain — данные интерфейса и расчёты.
- server — серверные операции, проверка доступа, работа с PostgreSQL, PDF, почтой и тесты; server/migrations содержит миграции.
- SPECIFICATION.md — действующее ТЗ; PROJECT_STATUS.md и CHANGELOG.md — состояние, проверки и передача между агентами.
- data — локальная база и конфиденциальные файлы, исключённые из Git.

Сайт поддерживает иврит и английский. Согласованные цены и правила расчёта приведены в разделе 0 SPECIFICATION.md; не заменяйте их историческими примерами.
