# Регламент откатов и версионирования (Rollback & Versioning Strategy)

Документ устанавливает правила фиксации версий, создания контрольных точек и выполнения быстрых и безопасных откатов для платформы Equipment Commerce & Rental Platform (PC-Lease).

---

## 1. Концепция безопасного версионирования

Для предотвращения потери данных и неконтролируемых изменений соблюдаются четыре уровня защиты:

1. **Git Tags (Теги релизов):** Каждый завершенный этап по ТЗ помечается аннотированным тегом (например, `v1.0.0`, `v1.1.0-crm`).
2. **Атомарные коммиты:** Каждый коммит содержит логически завершенное изменение с понятным префиксом (`feat:`, `fix:`, `docs:`, `refactor:`).
3. **Неизменяемые финансовые снимки (§ 6, § 30 ТЗ):** Подписанные договоры и финансовые проводки никогда не перезаписываются — исправления вносятся корректировочными записями.
4. **Expand / Contract для схемы данных (§ 2 ТЗ):** Изменения структуры данных всегда совместимы с предыдущей версией кода.

## 2. Сценарии отката (How to Rollback)

### Сценарий 1: Откат последнего ошибочного коммита (Safe Revert)
*Применяется, когда коммит уже был отправлен в репозиторий, но вызвал ошибку. История сохраняется, создается обратный коммит.*
```bash
# 1. Посмотреть хэш последнего коммита
git log -n 3 --oneline

# 2. Создать безопасный отменяющий коммит
git revert HEAD --no-edit

# 3. Отправить отмену в GitHub
git push origin main
```

### Сценарий 2: Возврат к стабильной контрольной точке по тегу (Release Tag Rollback)
*Применяется при необходимости срочно вернуть приложение к проверенной стабильной версии (например, `v1.1.0`).*

**Вариант А — Временный запуск и проверка старой версии в новой ветке:**
```bash
# Создать отдельную ветку от стабильного тега для анализа
git checkout -b rollback-inspection v1.1.0
```

**Вариант Б — Полный откат ветки main к стабильному тегу с сохранением резервной ветки:**
```bash
# 1. Сохранить текущее проблемное состояние в резервную ветку (backup)
git branch backup-before-rollback

# 2. Переместить указатель main на стабильный релизный тег
git reset --hard v1.1.0

# 3. Принудительно обновить main (если согласовано)
git push origin main --force
```

### Сценарий 3: Локальный откат незафиксированных изменений
*Применяется, если изменения в коде еще не отправлены и их нужно сбросить:*
```bash
# Сбросить все изменения в рабочей директории к состоянию последнего коммита
git reset --hard HEAD
git clean -fd
```

## 4. Рекомендации владельцу проекта

1. **Перед крупными изменениями:** Убедитесь, что текущее состояние засинхронизировано с GitHub.
2. **Создание релизного тега после проверки:** 
   ```bash
   git tag -a v1.1.0 -m "Release v1.1.0: Client CRM and Back Office"
   git push origin --tags
   ```
3. **Хранение секретов:** В репозиторий никогда не отправляются файлы `.env` с реальными ключами и паролями — они хранятся исключительно в переменных окружения хостинга.
